portal v0.8.2 fixes a credential bug that made "Allow & Remember" — and
therefore the whole Touch ID flow shipped in v0.7.0 — store an empty
password.

## Fixed: remembering a credential stored nothing

`Allow & Remember` has never actually worked. Storing the secret fed
`/usr/bin/security`'s interactive mode an `add-generic-password … -w`
command and put the password on the *next* line, expecting `-w` to prompt
for it. In interactive mode those prompts instead consume the remainder of
the **current** command line — which is empty — so they agreed on an empty
password, created the Keychain item with it, and only then failed by parsing
the secret as a command.

The visible result: portal reported the remember as failed (the audit line
downgraded to `source=prompt`), yet an item was left behind holding an empty
secret. The next `sudo` found that item, approved it with Touch ID, served
nothing, and `sudo` answered `Sorry, try again`.

v0.7.0 made this reachable for everyone by defaulting askpass enrollment to
`Allow & Remember`, but the defect predates it — every earlier remember
attempt failed the same way.

## What changed

- The secret is now a quoted argument of the same stdin command line.
  `security` parses that line itself, so the value still never becomes a
  process argument — verified by inspecting the `security` process's argv
  during a write.
- Storing an empty secret is refused outright.
- **Existing broken items self-heal.** An item holding an empty secret is now
  reported as absent, so the next request prompts for a real password and
  overwrites it, rather than serving nothing forever. You do not need to
  clean anything out of Keychain Access by hand.

After upgrading, the first `sudo` over ssh prompts for your password once
more (with `Allow & Remember` as the default); from then on Touch ID
releases the real secret.

portal v0.7.0 finishes the credential story: the remembered-credential
**click becomes a fingerprint**. Type your sudo password once; every later
sudo over ssh is approved with Touch ID (or your Apple Watch).

## New: Touch ID credential approval

`portal keychain`'s remember flow shipped in v0.4.0 with a click-to-approve
confirmation. That click is one Return keystroke — exactly the gesture
prompt-fatigue attacks train you to emit, and no proof the person at the
keyboard is you. Now:

- **Enrollment happens on the first typed sudo password.** When biometrics
  are available, the askpass dialog makes **"Allow & Remember"** the default
  and says plainly that remembering stores the credential in your Keychain
  and turns future approvals into a fingerprint. "Allow Once" is still one
  click away, and env/stdin credential requests keep the old default.
- **Every later request for that credential is a Touch ID sheet** —
  `LAPolicyDeviceOwnerAuthenticationWithBiometricsOrWatch` when available
  (so a paired Apple Watch works in clamshell), plain biometrics otherwise.
  The audit log distinguishes a fingerprint release (`keychain-touchid`)
  from a click (`keychain`).

**Fallback never gets worse than v1.** Cancel is a denial (with the usual
10s cooldown); a lockout, a failed match, a bridge error, or anything
unrecognized lands in the v1 confirmation dialog with whatever remains of
the shared 115-second budget. No path releases a secret without either a
biometric approval or an explicit click.

## How it works without a signed helper

The original cred design deferred Touch ID because LocalAuthentication
looked like it needed a signed native helper, and portal's release pipeline
is pure-Go `CGO_ENABLED=0` cross-compiled on Linux. It doesn't: unsigned
`osascript -l JavaScript` drives `LAContext` through the JXA ObjC bridge —
the same cgo-free shell-out portal already uses for clipboard and
notifications. No cgo, no entitlements, no new dependency, no signing lane.

Two consequences documented honestly in `DESIGN-cred-touchid.md`: the system
sheet is attributed to "osascript" (the reason text carries the portal
context), and the Keychain item itself is not re-bound to biometrics — Touch
ID gates *portal's* release decision, which is the prompt-fatigue surface,
not the same-UID threat the cred contract already excludes.

## Also

- New `cred-touchid` capability gate (default on; `portal features
  cred-touchid off` restores the pure click flow). `portal features` now
  lists 7 gates.
- `portal keychain list` reports Touch ID availability.
- **Zero wire change**: no new frames, verbs, or reasons; `ProtoVersion`
  stays 4 and the dev-box side is untouched. A Mac without biometrics runs
  the v1 flow byte-for-byte.
